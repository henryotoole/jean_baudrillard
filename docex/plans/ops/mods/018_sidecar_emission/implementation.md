# Mod 018 — Implementation steps

Goal: land the sidecar emit described in `overview.md`. After this mod, every core service is paired with an OTel Collector sidecar on both foundations, with the right config, the right env vars, the right secret wiring, and the right resource accounting.

The sub-agent executing this gets a fresh context — every step below is self-contained.

## Step 1 — Resolve the OTel Collector image digest

The sidecar image must be pinned by digest per [doctrine/infrastructure/specifics/telemetry_infra.md § Sidecar Image](../../../doctrine/infrastructure/specifics/telemetry_infra.md#sidecar-image).

1. Read the Docker Hub README for `otel/opentelemetry-collector` to identify the current recent-stable release. Use `WebFetch` against `https://hub.docker.com/r/otel/opentelemetry-collector` or the `OpenTelemetryCollector` tag listing.
2. Pick the most recent stable (non-`-rc`, non-dated/test) tag — e.g. `0.115.1` or whatever the README's "latest stable" indicates at execution time.
3. Resolve that tag's amd64 image digest. Two methods, pick what's available:
   - `docker manifest inspect otel/opentelemetry-collector:<tag>` from inside the docex container (if docker is reachable). The digest is the `digest:` field on the linux/amd64 platform entry.
   - `curl -fsSL https://hub.docker.com/v2/repositories/otel/opentelemetry-collector/tags/<tag>` and parse the JSON `images[].digest` for the linux/amd64 entry.
4. Record the resolved tag and digest. Format the constant value as:
   ```
   otel/opentelemetry-collector:<tag>@sha256:<hex>
   ```

If both methods fail (no network, no docker daemon), STOP and report — do not invent a digest. Mod 019's cut-walk can resolve it but the mod-018 implementation depends on it.

## Step 3 — Create `src/docex/emit/otelcol.py`

The module renders the sidecar config YAML. Single public function plus determinism helpers as needed.

```python
"""OTel Collector sidecar config rendering.

Produces the YAML config consumed by every sidecar in the project, in a
form suitable for two delivery mechanisms: a file mount on fixed (via
compose `configs:`) and an embedded env-var literal on elastic (via the
otelcol `env:` config provider).

Only the exporter destination differs by env: dev/test → debug exporter
writing to sidecar stdout; stage/prod → otlphttp targeting the project's
observability backend with API-key auth. See
doctrine/infrastructure/specifics/telemetry_infra.md § Per-Env Exporter
Configuration.
"""

from __future__ import annotations


def render_otelcol_config(env: str) -> str:
    """Return the OTel Collector YAML config for ``env`` as a string.

    Determinism: keys are emitted in a fixed order; no map iteration
    randomness reaches the output.
    """
    use_debug = env in ("dev", "test")
    exporter_name = "debug" if use_debug else "otlphttp"

    if use_debug:
        exporter_block = "  debug:\n    verbosity: detailed\n"
    else:
        exporter_block = (
            "  otlphttp:\n"
            "    endpoint: ${env:OBSERVABILITY_BACKEND_URL}\n"
            "    headers:\n"
            "      authorization: ${env:TELEMETRY_API_KEY}\n"
        )

    return (
        "# Generated by `docex compile`. Do not edit by hand.\n"
        f"# env: {env}\n"
        "receivers:\n"
        "  otlp:\n"
        "    protocols:\n"
        "      http:\n"
        "        endpoint: 127.0.0.1:4318\n"
        "processors:\n"
        "  batch: {}\n"
        "exporters:\n"
        f"{exporter_block}"
        "extensions:\n"
        "  health_check:\n"
        "    endpoint: 127.0.0.1:13133\n"
        "service:\n"
        "  extensions: [health_check]\n"
        "  pipelines:\n"
        f"    traces:  {{ receivers: [otlp], processors: [batch], exporters: [{exporter_name}] }}\n"
        f"    metrics: {{ receivers: [otlp], processors: [batch], exporters: [{exporter_name}] }}\n"
        f"    logs:    {{ receivers: [otlp], processors: [batch], exporters: [{exporter_name}] }}\n"
    )
```

The literal `${env:...}` substitutions are otelcol's own — they must appear in the output verbatim. Use *raw string literals* (or plain strings without an `f`-prefix in the relevant segments) to make sure no Python f-string substitution touches them. The implementation above is safe: the `f"..."` braces around `${env:...}` survive because Python only interpolates `{name}` (single braces), not `${...}`.

## Step 5 — Emit sidecar compose services and top-level `configs:`

File: `src/docex/emit/compose.py`.

1. Add an import at the top:
   ```python
   from docex import OTEL_COLLECTOR_IMAGE
   ```

2. In `emit_compose`, after the first pass populates `services: dict[str, Any]`, add a second pass that walks core services and appends a sidecar block per service. The sidecar block:

   ```python
   def _sidecar_block(svc: CompiledService, project: str, env: str) -> dict[str, Any]:
       sidecar_name = f"{project}_{env}_{svc.name}_otelcol"
       return {
           "image": OTEL_COLLECTOR_IMAGE,
           "container_name": sidecar_name,
           "command": ["--config=/etc/otelcol/config.yaml"],
           "network_mode": f"service:{svc.global_name}",
           "configs": [
               {"source": "otelcol_config", "target": "/etc/otelcol/config.yaml"},
           ],
           "environment": {
               # Empty default ({:-}) lets dev/test compose succeed without
               # the keys in .env — the debug exporter doesn't read them.
               "OBSERVABILITY_BACKEND_URL": "${OBSERVABILITY_BACKEND_URL:-}",
               "TELEMETRY_API_KEY": "${TELEMETRY_API_KEY:-}",
           },
           "healthcheck": {
               "test": ["CMD", "wget", "--spider", "-q",
                        "http://localhost:13133"],
               "interval": "10s",
               "timeout": "5s",
               "retries": 3,
           },
           "deploy": {"resources": {"limits": {"cpus": "0.1", "memory": "128M"}}},
           "restart": "unless-stopped",
           "logging": _LoggingAnchor(),
       }
   ```

3. Loop:
   ```python
   for name in sorted(compiled.services):
       svc = compiled.services[name]
       if not svc.is_core:
           continue
       sidecar_block = _sidecar_block(svc, compiled.project, compiled.env)
       services[f"{compiled.project}_{compiled.env}_{svc.name}_otelcol"] = sidecar_block
   ```

   Sidecars are NOT translated by `_translate_tree` — their `OBSERVABILITY_BACKEND_URL`/`TELEMETRY_API_KEY` values use compose's native `${VAR:-}` syntax, not docex's `$[VAR]` syntax. The translation pass would convert `$[VAR]` → `${VAR}`; since we already write `${VAR:-}`, skipping translation on sidecar blocks is correct. Wire this by populating `services[...]` after the `_translate_tree(block)` call so the translation has already run on its target, and the sidecar block survives untouched.

4. Add a top-level `configs:` section to the compose document:
   ```python
   # After `body_doc = {"services": services}` and the networks/volumes
   # additions:
   body_doc["configs"] = {
       "otelcol_config": {"file": "./otelcol-config.yaml"},
   }
   ```
   The file path is relative to the compose file's directory; the sidecar config sits beside `docker-compose.yml` in `infra/output/<env>/`.

5. **depends_on rewrite caveat:** the existing second pass rewrites every service's `depends_on` from short-form to long-form, resolving the target's global name from `simple_to_global`. Sidecars don't declare `depends_on` themselves, so they're untouched. But the core service's `depends_on` resolution path uses `simple_to_global.get(dep, dep)` — sidecars don't appear in `simple_to_global` (it's keyed by simple `name`), so this works as-is. No change needed.

6. **Network membership:** `network_mode: "service:<name>"` is *mutually exclusive* with a `networks:` list per docker-compose. The sidecar block above omits `networks:` — correct. Make sure no other emit path adds it.

## Step 8 — Resource accounting on elastic

File: `src/docex/cicl/compile.py`.

`_resources_to_elastic` currently takes a `Resources` and a `service_name` and returns a dict. Extend its signature with an `is_core: bool` parameter, defaulting to `False` for backwards compatibility:

```python
def _resources_to_elastic(
    res: Resources, *, service_name: str, is_core: bool = False
) -> dict[str, Any]:
    ...
```

Inside, before calling `fargate_pair`:

```python
# Sidecar overhead: every core service runs a paired otelcol sidecar at
# 0.1 vCPU / 128 MiB. The task-level totals must accommodate both
# containers; the core container still receives the requested resources
# at runtime. See doctrine/infrastructure/specifics/telemetry_infra.md
# § Task-Level Resource Allocation.
sidecar_cpu = 0.1 if is_core else 0.0
sidecar_mem_mib = 128 if is_core else 0

# Compute base + overhead in raw units, then round to Fargate tier.
req_cpu_units = max(1, int(round((res.cpu + sidecar_cpu) * 1024)))
req_mem_mib = _memory_to_mib(res.memory) + sidecar_mem_mib
```

Then call a new helper in `cicl/fargate.py` that accepts the requested values directly in Fargate units / MiB:

File: `src/docex/cicl/fargate.py`. Add alongside `fargate_pair`:

```python
def fargate_pair_from_units(
    cpu_units: int, memory_mib: int, *, service_name: str
) -> tuple[int, int]:
    """Translate already-computed (cpu_units, memory_mib) to a valid
    Fargate pair, rounding both up.

    Same shape as ``fargate_pair`` but skips the string parsing — useful
    when caller has already added per-task overhead (sidecar memory) and
    wants the rounding logic directly. Mod 018.
    """
    # (same algorithm as fargate_pair but starting from already-numeric
    # inputs)
    cpu_choice = _round_cpu_to_fargate(cpu_units)
    for cpu_attempt in [cpu_choice] + [
        c for c in _FARGATE_CPUS if c > cpu_choice
    ]:
        allowed = _allowed_memory_mib(cpu_attempt)
        for mib in allowed:
            if mib >= memory_mib:
                return (cpu_attempt, mib)
    max_cpu = _FARGATE_CPUS[-1]
    max_mib = _allowed_memory_mib(max_cpu)[-1]
    raise ValidationError([ValidationIssue(
        rule="rule_fargate_pair_invalid",
        message=(
            f"Fargate cannot satisfy cpu={cpu_units} units + memory={memory_mib} MiB: "
            f"exceeds Fargate maximum {max_cpu} units / {max_mib} MiB. "
            f"Reduce resources or split the service. Valid CPU buckets: "
            f"{list(_FARGATE_CPUS)}."
        ),
        where=f"core_services.{service_name}.resources",
    )])
```

Use it from `_resources_to_elastic`:

```python
cpu_units, memory_mib = fargate_pair_from_units(
    req_cpu_units, req_mem_mib, service_name=service_name,
)
```

Pass `is_core=isinstance(svc, CoreService)` from the call site in `compile_env`.

## Step 9 — Surface tier-rounding notice during compile

In `_resources_to_elastic`, after `fargate_pair_from_units` returns, detect rounding:

```python
# Surface a one-line notice when the sidecar overhead pushed the task
# into a higher Fargate tier than the bare-core request alone would
# have. Per doctrine/infrastructure/specifics/telemetry_infra.md
# § Fargate tier rounding.
if is_core:
    bare_cpu_units = max(1, int(round(res.cpu * 1024)))
    bare_mem_mib = _memory_to_mib(res.memory)
    bare_cpu_tier, bare_mem_tier = fargate_pair_from_units(
        bare_cpu_units, bare_mem_mib, service_name=service_name,
    )
    if cpu_units > bare_cpu_tier or memory_mib > bare_mem_tier:
        print(
            f"note: core service {service_name!r}: sidecar overhead "
            f"pushed task to next Fargate tier "
            f"({bare_cpu_tier} -> {cpu_units} vCPU units, "
            f"{bare_mem_tier} -> {memory_mib} MiB). The core container "
            f"still receives the requested {res.cpu} vCPU / {res.memory}; "
            f"the task-level totals carry the overhead."
        )
```

The print goes to stdout, the same stream `print(f"Compiled {len(_ENVS)} ...")` at the bottom of `run_compile` uses. No need for logging infra here.

Note: this prints once per env per service when the rounding hits. For a service compiled across two elastic envs (stage + prod), the same notice prints twice. That's fine — the operator sees the recurrence as a confirmation, not a duplicate.
