# Mod 021 — Embed otelcol config inline in compose via `configs.content`

## Problem

Mod 020 fixed the local-compose path so `docex test` brought sidecars up cleanly. But the same compose file lands on the deploy host during `release stage` / `release prod`, and on the host the file-mount path resolution differs:

| Context | `--project-directory` | Compose file location | Where `./infra/output/<env>/otelcol-config.yaml` resolves |
| ------- | --------------------- | --------------------- | ---------------------------------------------------------- |
| Local (`docex up`, `docex test`) | `<project_root>` | `<project_root>/infra/output/<env>/docker-compose.yml` | `<project_root>/infra/output/<env>/otelcol-config.yaml` ✓ |
| Deploy host (ansible-rendered) | `/opt/<project>/<env>/` | `/opt/<project>/<env>/docker-compose.yml` | `/opt/<project>/<env>/infra/output/<env>/otelcol-config.yaml` ✗ |

The ansible playbook renders the compose file and `.env` onto the host but not the otelcol config — so on the deploy host the bind-mount source doesn't exist:

```
Error response from daemon: invalid mount config for type "bind":
bind source path does not exist:
/opt/docex_smoke_fixed/stage/infra/output/stage/otelcol-config.yaml
```

We could fix this by also rendering the otelcol-config.yaml file onto the deploy host. But the directory layouts don't match (no `infra/output/<env>/` tree under `/opt/...`), and "render two files plus their relative layout" is more machinery than the doctrine wants here.

Cleaner: switch from compose's `configs.<name>.file:` (bind-mount from disk) to `configs.<name>.content:` (literal inline YAML). The compose file becomes self-contained. Same shape on local and deploy host. Path resolution stops being a concern.

Compose v2.23+ supports `configs.<name>.content:` (released 2023-12). The local docker compose v2 v5.1.3 is well past that.

This also makes the two foundations symmetric: elastic already embeds the otelcol config as a literal in `OTEL_CONFIG_YAML` (per mod 018's HCL emit). After mod 021, fixed embeds it as a literal in `configs.otelcol_config.content`. Same source of truth (`render_otelcol_config(env)`), no separate file written.

## Scope

In scope:

1. **`emit/compose.py`**: emit `configs.otelcol_config.content: <multiline YAML>` instead of `configs.otelcol_config.file: ./...`. Source the content from `render_otelcol_config(env)`, the same function elastic already uses.
2. **`cicl/compile.py::run_compile`**: stop writing `infra/output/<env>/otelcol-config.yaml` as a separate file. The config now lives in the compose YAML.
3. **`tests/unit/test_compose_sidecar.py`**: update `test_compose_has_top_level_configs_block` to assert on `content:` rather than `file:`. The content equals `render_otelcol_config(env)`.
4. **CHANGELOG**: append to `[Unreleased] § Fixed` (mod 020's section).

Out of scope:

- Anything elastic-side. Elastic already embeds the config inline via `OTEL_CONFIG_YAML`. No change.
- The sidecar's compose-side `configs:` reference (`source: otelcol_config, target: /etc/otelcol/config.yaml`). That stays — the *delivery* mechanism inside the sidecar is `target: /etc/otelcol/config.yaml` regardless of whether the source is a file or inline content.

## Design

### Compose-side change

Before (mod 020 form):
```yaml
configs:
  otelcol_config:
    file: ./infra/output/<env>/otelcol-config.yaml
```

After (mod 021):
```yaml
configs:
  otelcol_config:
    content: |
      # Generated by `docex compile`. Do not edit by hand.
      # env: <env>
      receivers:
        otlp:
          protocols:
            http:
              endpoint: 127.0.0.1:4318
      processors:
        batch: {}
      exporters:
        debug: ...   # or otlphttp for stage/prod
      ...
```

The YAML dumper emits `content:` as a literal block scalar (`|`) to preserve the multi-line shape. PyYAML handles this automatically for strings with embedded newlines.

### File-write change

Drop:
```python
(env_dir / "otelcol-config.yaml").write_text(render_otelcol_config(env))
files_written += 1
```

…from `run_compile`. The function `render_otelcol_config` stays — it's used by both compose emit and HCL emit.

### Compile output layout (after mod 021)

```
infra/output/<env>/
├── docker-compose.yml         (fixed envs; embeds otelcol config inline)
├── playbook.yml               (fixed stage/prod)
├── inventory.yml              (fixed stage/prod)
├── ansible.cfg                (fixed stage/prod)
└── main.tf                    (elastic stage/prod; embeds otelcol config inline via HCL env var)
```

No more `otelcol-config.yaml` standalone file. Operators can still inspect the rendered config — it lives at the top of each `docker-compose.yml`'s `configs:` block (and elastic's `OTEL_CONFIG_YAML` env entry in `main.tf`).

## Risk and rollback

- **Compose version dependency:** `configs.<name>.content:` requires compose v2.23+ (released 2023-12). Our shipped tooling uses v2 v5.1.3 (per `docker/subprocess_client.py`), which is well past 2.23.
- **Inline YAML inside YAML:** the embedded otelcol config contains lines like `${env:OBSERVABILITY_BACKEND_URL}` (otelcol's own env-substitution syntax). These survive YAML quoting because they're inside a literal block (`|`) — neither compose nor PyYAML interprets `${env:...}` inside a string scalar. Compose's own `${VAR}` interpolation likewise won't touch it (the literal block keeps it verbatim, and compose only interpolates in flow-scalar positions).
- **Rollback:** revert the mod. Restores the separate file path of mod 020.

## What this mod does NOT do

- Does not change elastic. Elastic embeds the config via `OTEL_CONFIG_YAML` env var; that's existing mod 018 behavior, unchanged.
- Does not touch the sidecar block's `configs:` reference (`source: otelcol_config`). Only the top-level `configs:` declaration changes.
- Does not change the rendered YAML's content. `render_otelcol_config(env)` produces the same string as before; only its delivery mechanism changes.
- Does not modify the ansible playbook. The deploy-host shape gets simpler: docker-compose.yml + .env, nothing else.
