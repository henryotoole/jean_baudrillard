## Context for a fresh agent

You are working in the `docex` project at `~/.claude/jean_baudrillard/docex/`. `docex` is the executor of the doctrine; full background is in `plans/core/masterplan.md` and `plans/core/docex_process.md`. The doctrine itself lives at `~/.claude/jean_baudrillard/doctrine/`.

**The bugs.** Three docex code changes and three doctrine/checklist prose updates. All surfaced by the C.7 walk of `test_projects/fixed`. Details and design rationale are in `overview.md`. Briefly:

1. **Image: collection install path.** The Dockerfile already installs `community.docker:==3.10.4` but uses `ansible-galaxy collection install` without `-p`, putting it under `/root/.ansible/collections`. At runtime the in-container user is the operator (uid != 0), whose HOME is `/home/<operator>` — a directory the image doesn't have. Ansible's collection lookup misses the collection and reports `Unable to resolve module/action 'community.docker.docker_compose_v2'`.
2. **Image: HOME-write needs.** Ansible-core writes to `$HOME/.ansible/tmp` and `$HOME/.ansible/cp` by default. Image's `/home` is root-owned with no `/home/<operator>` subdir. Redirect via env vars.
3. **Emitter: deprecated `stdout_callback = yaml`.** Removed from `community.general` 12.0.0. Use the modern ansible-core equivalent.
4. **Emitter: migration task.** Currently uses `community.docker.docker_container` with `auto_remove: true` and an `env_file` that only carries POSTGRES_* secrets. Missing the compile-time-resolved DATABASE_* env vars from the web service's compose `environment:` block, AND masks failure modes. Replace with `docker compose run --rm <service> /service/migrate.sh` via `ansible.builtin.command` — inherits the service's full environment by definition.
5. **Doctrine/checklist:** Three prose edits. Wording is operator-approved verbatim; do not rephrase.

Two adjacent issues are already inline and folded into this mod:

6. The uncommitted `PRE_CUT_CHECKLIST.md § A.2.1` addition (test projects must be own git repos with v0.0.1 tag) gets bundled into the mod 003 commit alongside the other checklist edits.

```dockerfile
# Install the community.docker Ansible collection at the system-wide
# collections path. We install at /usr/share/ansible/collections rather
# than the default $HOME/.ansible/collections because the in-container
# user at runtime is the operator's uid (not root), whose HOME is
# /home/<operator> — a directory the image does not provide. Ansible
# checks the system path during module resolution regardless of HOME
# state, so collections installed here are always available.
```

Then immediately after the `git config --system --add safe.directory '*'` line (currently line 105), add these env vars before the `WORKDIR /` line:

```dockerfile
# Redirect ansible's runtime scratch (per-run tmp dir, control sockets)
# to /tmp rather than $HOME/.ansible/{tmp,cp}. The image's /home is
# root-owned and the operator's HOME path doesn't exist as a writable
# directory at runtime — ansible-core's default scratch paths would
# fail with EACCES. /tmp is always present, writable by any uid, and
# the right place for per-run ephemera.
ENV ANSIBLE_LOCAL_TEMP=/tmp/.ansible-tmp
ENV ANSIBLE_PERSISTENT_CONTROL_PATH_DIR=/tmp/.ansible-cp
```

### 3. Playbook template — `docker compose run` for migrations

File: `src/docex/emit/templates/playbook.yml.j2`

Find the migration task block (currently lines 37–50):

```jinja
{% for svc in core_services_with_schema %}
    - name: Run migrations for {{ svc.name }}
      community.docker.docker_container:
        name: "{{ '{{' }} project {{ '}}' }}_{{ '{{' }} env {{ '}}' }}_{{ svc.name }}_migrate"
        image: "{{ image_for(svc) }}"
        command: /service/migrate.sh
        networks:
          - name: "{{ '{{' }} project {{ '}}' }}_{{ '{{' }} env {{ '}}' }}_internal"
        env_file: "{{ '{{' }} deploy_root {{ '}}' }}/.env"
        detach: false
        auto_remove: true
      tags:
        - migrate
{% endfor %}
```

Replace with:

```jinja
{% for svc in core_services_with_schema %}
    - name: Run migrations for {{ svc.name }}
      ansible.builtin.command:
        cmd: docker compose run --rm {{ svc.name }} /service/migrate.sh
        chdir: "{{ '{{' }} deploy_root {{ '}}' }}"
      register: {{ svc.name }}_migrate_result
      changed_when: true
      tags:
        - migrate
{% endfor %}
```

Why this is correct: `docker compose run --rm <service> <cmd>` creates a one-off container from the same compose service definition the regular stack uses — inheriting image, the full `environment:` block (compile-time-resolved `DATABASE_HOST`/`DATABASE_PORT`/`DATABASE_NAME`), the `env_file:` reference (runtime `POSTGRES_USER`/`POSTGRES_PASSWORD`), networks, depends_on. `--rm` cleans up after; `ansible.builtin.command` captures rc/stdout/stderr regardless of exit code. The `register: <svc>_migrate_result` allows downstream tasks to reference the migration's output if needed. `changed_when: true` reflects that migrations are state-changing by nature.

The `image_for(svc)` jinja helper is no longer needed for the migration task — compose run picks the image from the compose file. If `image_for` is only used by this template, search for unused helper references; if used elsewhere, leave it.
