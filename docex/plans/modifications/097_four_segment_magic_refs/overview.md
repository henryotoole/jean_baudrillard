# Mod 097 — Four-segment magic refs

Phase 2 of the **service process types** advance
([plan](../../advances/004_next/service_processes_implementation_plan.md),
[design record](../../advances/004_next/service_processes_refactor.md)).
The rule of record is [`cicl.md § Magic Refs`](../../../../doctrine/infrastructure/cicl.md)
as written by Mod 094; where the design record and the doctrine differ in
wording, the doctrine wins. **No doctrine file is touched by this mod.**

## Goal

Make `${core_services.<svc>.<proc>.<part>}` resolve. Mod 096 re-keyed the
resolver's contexts and engines onto the two-segment compiled identity and left
a bare three-segment core ref failing honestly; this mod fills the seam marked
at `magic_refs.py:159`.

Baseline to beat: **821 passed** (`pytest tests/unit`), verified before design.

## The grammar

```
${core_services.<service>.<process>.<part>}      # four segments — api.web.host
${backing_services.<service>.<part>}             # three segments — database.host
```

Asymmetric and honest: a backing service has no process types, so there is
nothing to qualify.

### Parse generically, then arity-check by kind

Not a widened regex. Widening re-creates the class of confusing failure Mod 096
just fixed at one site, and it leaves the *fall-through* hole open. The pattern
becomes **kind-prefixed and body-agnostic**:

```python
_MAGIC_RE = re.compile(r"\$\{(core_services|backing_services)\.([^{}$]*)\}")
```

Everything beginning `${core_services.` or `${backing_services.` is therefore
**claimed** by the magic-ref parser, whatever its shape. The body is split on
`.` and arity-checked against the kind:

| Kind | Segments | Wrong-arity message |
| ---- | -------- | ------------------- |
| `core_services` | exactly 3 | *"`core_services` refs take `<service>.<process>.<part>`; got `api.host` (2 segments) — did you mean `${core_services.api.<process>.host}`? A codebase has no single boundary, so a bare name has no answer. See cicl.md § Magic Refs."* |
| `backing_services` | exactly 2 | *"`backing_services` refs take `<service>.<part>`; got `db.web.host` (3 segments) — a backing service has no process types, so there is nothing to qualify. See cicl.md § Magic Refs."* |

The two messages are generated by **one** arity checker so they cannot drift
into non-siblings. Segments are checked non-empty; beyond that no charset
policing happens at parse time — an odd segment resolves to the existing
"unknown service" / "unknown process" / "does not expose part" errors, which
already name what was looked up. Keeping charsets out of the pattern is the
point: a second charset is the thing that produced the asymmetry below.

### Why this closes the fall-through hole

Verified against the current tree, post-096. Row three is the important one, and
it is not a message-quality problem: a hyphenated four-segment ref matches
**neither** regex today and is therefore **written verbatim into the emitted
`docker-compose.yml` / `.tf` as literal text**. That is silent corruption of
infrastructure config — the compiler produces output that looks valid, applies,
and carries a `${…}` string where a hostname belongs. This is the strongest
argument for generic capture, and the reason the capture must be
**body-agnostic**: whether a string *is* a magic ref has to be decided
independently of whether that ref is well-formed. Coupling the two is what let a
malformed ref escape being seen at all.

| Ref | Today | After |
| --- | ----- | ----- |
| `${core_services.api.host}` | `_MAGIC_RE` hit → 096's bare-core error | arity error (same content, one generator) |
| `${core_services.api.web.host}` | `_MAGIC_RE` miss (its part group forbids `.`) → falls through to `_COMPILE_RE`, which *does* match, so it dies as *"undefined compile-time variable ${core_services.api.web.host} … available: [apex_domain, env_name, …]"* | resolves |
| `${core_services.my-api.web.host}` | matches **neither** regex (`_COMPILE_RE` forbids `-`) → **passes through silently into the emitted compose/HCL as literal text** | resolves |
| `${backing_services.my-db.host}` | resolves (`_MAGIC_RE` permits `-`) | resolves |

The third row is the live asymmetry the C.O. flagged, and it is the worst of the
four: not a bad message but *no* message. Kind-prefixed generic capture removes
it structurally — a hyphen can no longer decide whether a ref is seen at all.

### One more line in `substitute.py` — C.O. ruling: take it

`_COMPILE_RE` (`substitute.py:38`) also gains `-` in its charset, so that a
*non*-magic leftover such as `${some-var}` raises the honest undefined-variable
error instead of surviving into output.

**Scope this correctly in the record.** After generic capture, the widening is
**not** what fixes the magic-ref hole — capture fixes that structurally, and
would fix it with `_COMPILE_RE` untouched. The widening's residual value is
narrower: a **mistyped compile-time variable** (`${env-name}` for `${env_name}`)
becomes a compile error rather than a literal emitted into infrastructure
config. Smaller than the magic-ref case, the same failure class, and worth
having — but it should not be credited with the fix above.

Reasons it is worth taking now (C.O.): the behavior removed is silent
pass-through and the behavior added is a loud, well-worded compile error, which
is this advance's whole thesis; two regexes disagreeing about what a valid
identifier is, is a latent trap whether or not anything currently steps in it;
and this is a breaking-format minor with an upgrade guide already being written,
so a documented behavior change will never be cheaper.

Blast radius, checked before committing to it: the only `${…}` literals docex
emits that must survive verbatim are compose's own `${TELEMETRY_API_KEY:-}`
(`compose.py:226`) and `${TRAEFIK_ACME_EMAIL:-}` (`compose.py:806`). Both are
written at *emit* time, downstream of all substitution, and both contain `:`,
which the widened charset still excludes. No shipped transfer table and no
`test_projects` project-local table contains a `${…}` with a hyphen inside
(grepped).

#### No escape hatch exists, and none is added

Checked, because a widened charset is only safe to ship if an author who
genuinely wants a literal `${a-b}` has somewhere to go. **There is none.** The
substitution grammar has exactly three syntaxes — `${var}`, `$[var]`, `@expr`
(`substitute.py:1-26`) — and no escape form. The `$$` doubling that exists in
the tree (`compose.py:288,629`; `hcl.py:94,1196`) is applied by *emitters*,
after substitution, to escape Compose's and HCL's **own** interpolators; it is
not an input-level escape and `_resolve_compile_time` never sees it.

So the error message must not offer a workaround that does not exist. It names
what was undefined and where, and stops there. Stated plainly here so **Mod
107's upgrade guide documents both the change and the absence of a workaround** —
a known sharp edge described honestly, rather than one discovered from a
downstream project. If a literal `${a-b}` is ever genuinely needed, adding a
`$${…}` escape is a grammar change and therefore a doctrine change; it is not
smuggled in here.

  None` — `None` for backing targets. `consumer` is documented as what Mod 096
  already made it: the **compiled process identity** (`api-web`) for a core
  consumer, the service name for a backing one. No call-site change; `compile.py`
  already passes the compiled key.
- **Cycle guard** (`:75`, used `:102-111`) keyed on `(kind, target, process,
  part)`.
- **`_resolve_part`** takes `process` and, for `kind == "core_services"`, looks
  up `doc.core_services[target].processes[process]`, then reads `engines` /
  `contexts` under `ProcessRef(target, process).compiled`. Unknown process gets
  its own message listing the codebase's known process types.
- **`find_magic_refs`** returns richer matches (kind + raw body + a `parse()`
  that performs the arity check). Its one caller (`validate.py:276`) and its one
  test (`test_magic_refs.py:121`) change shape with it. The arity message is
  raised as a `SubstitutionError` subclass from `parse()` so the resolver
  propagates it and the validator catches it into a `ValidationIssue` — one
  message, two surfaces, no duplicated string.

## Self-references rejected

A process type may not reference its own part. The message hints at `localhost`
and carries the doctrine's actual reason, not just "it is degenerate":
`provides.host` is the **internal** discovery name, so the one plausible motive —
building an absolute URL to oneself — would not return what the author expects.

Enforced in **both** layers, as Mod 096 did for the bare-core case: the resolver
raises, the validator issues. Mod 094 already wrote the sibling clause for
`consumes` (`cicl.md` rule 25); this message is drafted from `cicl.md § Magic
Refs` so that Mod 098's self-consume message can be written to match it.

Consequence worth stating: a **service-level** `env:` ref to one of the
codebase's own process types is now illegal, because the service-level surface
is resolved once per process type and self-ref trips on that process's own pass.
That is the correct reading of doctrine (the ref would oblige every process type
to declare an edge to a sibling, including itself) and it needs no extra code.

## Validation (`validate.py`)

`_validate_magic_refs` gains the core-target branch that Mod 096 stubbed out:

- **Rule 3** for core targets — the service exists, the named process exists,
  and the part is exposed by the engine(s) of that process's `role` (collected
  across foundations, exactly as the backing branch does today).
- **Rule 7 is not extended to core targets in this mod.** A core ref must be
  matched by a `consumes` entry, and `consumes` does not exist until Mod 098;
  `depends_on` is backing-only since Mod 096's rule 24, so there is nothing
  correct to check against. The branch carries a comment naming Mod 098. Rule 7
  for backing targets is untouched.
- **Rule id unification.** 096's `rule_3_bare_core_magic_ref` is folded into
  `rule_3_magic_ref_arity`, since the bare-core case is now one output of the
  shared arity checker rather than a special case.
  `test_process_nesting.py:478` is retargeted to the new id; its *message*
  assertion is unchanged, which is the assertion that carried the intent.
- Self-reference issues under `rule_3_self_magic_ref`, following the precedent
  096 set of filing magic-ref well-formedness under rule 3.

## Free behavior, pinned

A ref to a `scheduler` process type fails with no new resolution code:
`scheduler/container` declares `provides: {}`, so the part lookup finds nothing.
Because `known: []` reads as a puzzle rather than an answer, the
"does not expose part" error gains one clause when the engine exposes *no* parts
at all — that the role publishes nothing and therefore cannot be a magic-ref
target. A test pins the failure so a future change to the scheduler table cannot
silently open it.

## Tests

At minimum, on top of the mechanical churn:

1. `${core_services.api.web.host}` resolves, on fixed **and** elastic.
2. Three-segment core ref → the arity message (resolver **and** validator).
3. Four-segment **backing** ref → the mirror-image message.
4. Hyphenated names round-trip: `${core_services.my-api.web.host}` and
   `${backing_services.my-db.host}` both resolve, and the emitted value contains
   no surviving `${`.
5. Self-ref rejected, message names `localhost` (resolver and validator).
6. A cycle through **two process types of the same codebase** is detected —
   `api.web`'s provides template referencing `api.worker` and back.
7. A ref to a `scheduler` process type fails.
8. `MagicRefDependency` records `target_process`, and `consumer` is the compiled
   identity.
9. `${some-var}` raises the undefined-compile-time-variable error rather than
   passing through (the widened `_COMPILE_RE`).

Green at **821 or more**. No test deleted or skipped to get there.
