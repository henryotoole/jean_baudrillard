# api — db schema

The `api` **codebase** owns the schema of the project's relational database backing service, `appdb` (postgres 15). `schema_owned_by` names a codebase, never a core service — `migrate.sh` runs once per codebase, not once per invocation.

## Tables

### `pings`

Stores each ping created by `POST /pings` until the `api.worker` core service processes it.

| Column | Type | Notes |
| ------ | ---- | ----- |
| `id` | `uuid` | Primary key. Generated by `api.web` at write time with `uuid4` (random; the table's ordering comes from `created_at`, not from the key). |
| `payload` | `text` | The request body, stored verbatim as a string. Schema is intentionally not validated past "it's a string" — keeps domain surface trivial. |
| `created_at` | `timestamptz` | Defaults to `now()`. |
| `processed_at` | `timestamptz` | `NULL` until `api.worker` claims and processes the row; set to `now()` at that point. Also the retention key the `prune_pings` job reaps against — only a *processed* ping is ever eligible. |

### `jobs`

The deferred-work queue. `api.clock` inserts a row when a scheduled job fires; `api.worker` claims it and performs it. The table **is** the transport: the doctrine ships no `queue` backing-service role, so a postgres table owned by the enqueueing codebase is the queue.

That ownership is the reason this table lives in `api` at all. A clock may only enqueue onto its own codebase's queue, because only the codebase that owns a schema may write to it — which is why the retired `reaper` codebase could not become a clock and why the clock folded into `api` instead (`clock.md § The clock defers; it does not work`).

| Column | Type | Notes |
| ------ | ---- | ----- |
| `id` | `uuid` | Primary key. Generated by the enqueueing process. |
| `name` | `text` | The job name — the same identifier that keys `schedules:` in `infra.yml` and the dispatch tables in code. No payload column: the clock defers a *name*, and the worker looks that name up in its own table. |
| `enqueued_at` | `timestamptz` | Set by the enqueueing process. Defaults to `now()`. |
| `started_at` | `timestamptz` | `NULL` until claimed. Stamped inside the claiming transaction, which is what makes the claim exclusive. |
| `finished_at` | `timestamptz` | `NULL` until the job terminates, set on success *and* on failure. |
| `error` | `text` | `NULL` on success; the failure text otherwise. A failed job is recorded on its row rather than lost to a traceback, and the drain continues past it. |

**Index.** `jobs_pending_idx` on `(enqueued_at)` is **partial** — `WHERE started_at IS NULL`. The worker's claim only ever reads unstarted rows, so the index covers exactly the hot query and stops growing as completed jobs accumulate.

**Claiming.** `SELECT … FOR UPDATE SKIP LOCKED` inside one transaction, then `UPDATE … SET started_at`. `FOR UPDATE` buys exclusivity (`api.worker` runs `replicas: 2` in prod, so this is a genuine two-consumer race); `SKIP LOCKED` buys liveness (without it the second worker blocks behind the first's batch instead of taking different rows). See [`hex/jobs.md`](./hex/jobs.md#concurrency).

**Retention of the queue itself** is deliberately not implemented. Rows accumulate; the smoke project is torn down between walks. A real project would prune finished jobs — most likely with a scheduled job of its own.

### `schema_migrations` (managed by dbmate)

Maintained automatically by dbmate; lists applied migration filenames. Not application-visible.

## Migrations

All migrations live at `core/api/migrations/*.sql` and are versioned by timestamp prefix per dbmate's convention. The first migration creates the `pings` table; subsequent migrations evolve it.

Doctrine requirement: migrations are idempotent and **forward-only** (`databases.md`) — the doctrine never reverses a schema, even on rollback, and `docex rollback` runs no migration at all. Each migration file still declares both `-- migrate:up` and `-- migrate:down` because that is dbmate's file format; the `down` half is not a rollback path the pipeline ever takes.
