# api — db schema

The `api` **codebase** owns the schema of the project's relational database backing service, `appdb` (postgres 15 — RDS on elastic `stage`/`prod`, a postgres container on `dev`/`test`). `schema_owned_by` names a codebase, never a process type — `migrate.sh` runs once per codebase, not once per invocation.

## Tables

### `pings`

Stores each ping created by `POST /pings` until the `api.worker` process type processes it.

| Column | Type | Notes |
| ------ | ---- | ----- |
| `id` | `uuid` | Primary key. Generated by `api.web` at write time (`uuid7` for time-ordered insertion). |
| `payload` | `text` | The request body, stored verbatim as a string. Schema is intentionally not validated past "it's a string" — keeps domain surface trivial. |
| `created_at` | `timestamptz` | Defaults to `now()`. |
| `processed_at` | `timestamptz` | `NULL` until `api.worker` claims and processes the row; set to `now()` at that point. Also the retention key `reaper.prune` reaps against. |

### `schema_migrations` (managed by dbmate)

Maintained automatically by dbmate; lists applied migration filenames. Not application-visible.

## Migrations

All migrations live at `core/api/migrations/*.sql` and are versioned by timestamp prefix per dbmate's convention. The first migration creates the `pings` table; subsequent migrations evolve it.

Doctrine requirement: migrations are idempotent and reversible (`databases.md`). Each migration file declares both `-- migrate:up` and `-- migrate:down`.
